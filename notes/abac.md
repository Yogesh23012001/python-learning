"I would enforce tenant isolation inside the vector database query itself using metadata filtering, for example WHERE tenant_id = ? ORDER BY embedding <=> query LIMIT k. This ensures similarity search is performed only within that tenant's corpus. Filtering after retrieval is unsafe because it risks cross-tenant data leaks if the filter is bypassed, and it also degrades retrieval quality by discarding top-ranked chunks from other tenants after the search. The correct approach is to make unauthorized chunks unreachable rather than filtering them after the fact."


There are two reasons WHERE-clause filtering beats retrieve-then-drop, and you named both across the week:
1. Security (the obvious one): Post-filtering means the wrong tenant's data was retrieved and you're trusting application code to drop it. One bug, one forgotten filter, one code path that skips the drop step — and it leaks. WHERE-clause filtering means the wrong data was never a candidate. The leak is structurally impossible, not prevented by diligence. Defense by unreachability.
2. Quality (the subtle one — your insight): Even if post-filtering works perfectly, it silently degrades retrieval. If you retrieve top-5 and 2 belong to another tenant, you drop them and the user gets top-3, not top-5. Their 4th and 5th best chunks were never fetched — the slots got "used up" by another tenant's chunks that then got discarded. WHERE-clause filtering means all 5 returned slots are the user's actual top-5, because the database only ever ranked the user's chunks. Post-filtering robs the user of retrieval depth; pre-filtering preserves it.
That second point is the one you reached for in your explanation, and it's the one that signals depth. Anyone can say "filter for security." Noticing that post-filtering also quietly degrades result quality — that your top-k silently shrinks — is the systems-level observation. Both reasons point to the same architecture, and you can now give both.
The interview-ready version: "I enforce tenant isolation in the vector query's WHERE clause, before the LIMIT — for two reasons. First, security: the wrong tenant's chunks are never candidates, so a leak is structurally impossible rather than prevented by careful filtering code. Second, quality: post-filtering would let another tenant's chunks consume slots in the top-k and then get dropped, silently shrinking the user's effective results — pre-filtering guarantees all k returned chunks are the user's actual best matches. Same principle I applied to partner-bank data isolation at NPCI: make the wrong data unreachable, don't trust the app to filter it."
